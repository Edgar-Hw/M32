## Exact Root Cause

Pinned WIE `net/wie/Launcher` is a Rust-backed Java class and starts the guest with:

```text
jvm.new_class(main_class, "()V", ())
```

Pinned RustJava resolves a normal `new_class()` request through the calling Java class's defining
class loader.

For `net/wie/Launcher`, that loader is:

```text
org/rustjava/lang/RustJarClassLoader
```

Pinned `RustJarClassLoader::findClass()` intentionally ignores classpath items that do not end in:

```text
.rustjar
```

Therefore an ordinary application JAR such as:

```text
j2me-first-frame-running.jar
```

was never queried.

That behavior exactly explained:

```text
filesystem calls: []
```

## FIX3/FIX4 — RustJava System Loader Compatibility

M32 already vendors the exact RustJava base revision for reproducibility.

A narrow documented compatibility patch was applied to:

```text
third_party/rustjava/jvm/src/jvm.rs
Jvm::current_class_loader()
```

When the current caller loader is exactly:

```text
org/rustjava/lang/RustJarClassLoader
```

class resolution uses the already-created system class loader instead.

Pinned RustJava constructs the system loader as:

```text
URLClassLoader(parent = RustJarClassLoader)
```

Resulting topology:

```text
WIE/MIDP RustJar classes
-> parent RustJarClassLoader

guest application .jar classes
-> system URLClassLoader
```

The base revision marker remains:

```text
ba5797b8eb4cf376fdd63129903d319d1d7acf98
```

Local compatibility patch provenance:

```text
third_party/rustjava/M32_LOCAL_PATCHES.md
```

Apply/verify scripts:

```text
scripts/apply-rustjava-system-loader-compat.ps1
scripts/verify-rustjava-system-loader-compat.ps1
```

FIX4 only made the safe patch application mechanism robust to newline/source formatting while still
requiring the exact base revision and exactly one expected source fragment.
